# Спринт 8. InsureTech

## Исходные данные

*Перенёс факты из описания бизнеса, чтобы можно было ссылаться на них из заданий.*

### О компании

InsureTech -- агрегатор страховых услуг. Работает с частными и корпоративными клиентами:

- частным клиентам предлагает сайт для подбора и оформления страховок,
- корпоративным клиентам и партнёрам предоставляет API для интеграции страховых услуг.

Основной продукт -- страхование жизни. Компания успешно запустила MVP и планирует развиваться; в ближайшее время -- большая рекламная кампания.

### Компоненты

- **core-app** -- монолитный бэкенд: отображение продуктов, оформление заявок, отображение оформленных страховок.
- **client-info** -- сервис клиентских данных: передаёт данные core-app, вносит и редактирует данные в личном кабинете.
- **ins-product-aggregator** -- интеграция со страховыми компаниями (сейчас пять), единый API по продуктам и предложениям ОСАГО.
- **ins-comp-settlement** -- взаиморасчёты со страховыми компаниями, раз в месяц отправляет перечень оформленных страховок.
- Веб-приложение для клиентов.

### Инфраструктура

- Kubernetes, одна зона доступности.
- PostgreSQL на отдельной ВМ, единственный экземпляр; каждая сервисная схема отдельная.
- REST между фронтендом и бэкендом; партнёрский API напрямую через LoadBalancer Kubernetes, доступен из интернета.

### Проблемы

- **П1.** Сайт медленно загружает страницы под нагрузкой (поиск до 50 RPS, оформление до 10 RPS); страдают NPS и retention.
- **П2.** Нарушается SLA для B2B-клиентов: один партнёр поднимал нагрузку до 250 RPS при договорных 20 RPS и «съедал» ресурсы приложения.
- **П3.** Приложение падает, о простоях узнают от пользователей; час простоя -- около 500 тысяч рублей убытка плюс репутационные потери.

## Задания

### Задание 1. Технологическая архитектура

- [ ] `Task1/` -- drawio-схема «InsureTech_технологическая архитектура_to-be» (нотация Yandex Cloud), на которой отражены:
  - стратегия масштабирования и отказоустойчивости под требования: RTO 45 мин., RPO 15 мин., SLA 99,9%, все часовые пояса РФ, одинаковая скорость загрузки страниц, объём данных 50 GB;
  - конфигурация Kubernetes (независимые кластеры или растянутый) с комментарием о выборе;
  - балансировка нагрузки со всеми health check;
  - фейловер-стратегия на уровне взаимодействия клиента с приложением;
  - конфигурация БД: репликация и резервное копирование;
  - решение по шардированию БД.
